### 3. Latency: What causes it and is yours optimized?
TypeORM (your database connector) is notoriously famous for hidden latency issues. Latency often stems from:
1. **The N+1 Query Problem:** Automatically querying the `causes` table line-by-line for every single stop, rather than using an `INNER JOIN`.
2. **Heavy Object Mapping:** TypeORM taking raw SQL rows and spending hundreds of milliseconds trying to instantiate heavy TypeScript Class Objects before returning them.
3. **Full Table Scans:** Executing a `TIME_TO_SEC` string diffing function over hundreds of thousands of un-indexed rows inside MySQL.

**Is your SQL optimized right now?**
**YES. It is extremely well optimized.** The developer specifically stripped out TypeORM's default features to squeeze out maximum speed.

Here are the specific "tricks" used in your code to eliminate latency:

1. **Bypassing the ORM entirely (`this.dataSource.query`):** Instead of using TypeORM's `.find()` or QueryBuilder which drags memory, they wrote raw MySQL directly. This drastically cuts down the JS execution time.
2. **Pre-Computed Duration (`IFNULL(s.Duree, 0)`):** Instead of making the database calculate the difference between `startTime` and `stopTime` inside the SQL statement via `TIMESTAMPDIFF`, your database actually contains a pre-calculated `Duree` column. Simply fetching a static integer rather than computing it on the fly is a massive speed boost.
3. **Raw `INNER JOIN`:** It explicitly forces MySQL to combine data on an index (`c.id = s.cause_id`) efficiently, preventing the N+1 problem.
4. **Dynamic String Construction:** It dynamically builds the `WHERE` statement array in JavaScript (`whereParts.push(...)`). This prevents SQL injection parameters while guaranteeing MySQL only evaluates conditions that are strictly necessary, allowing the database to hit its B-Tree Index quickly.

Nous avons résolu un problème classique de performance des bases de données appelé "Le piège de la non-SARGabilité et des jointures massives".

Voici les 4 grandes étapes de l'optimisation, du problème initial à la solution finale :

1. Le Problème Initial : La fonction dans le WHERE (Non-SARGable)
Dans la première version, pour gérer le décalage de l'équipe de nuit (qui commence à 22h et finit à 06h le lendemain), nous avions une fonction SQL "à la volée" : IF(Debut < '06:00:00', DATE_SUB(Jour, INTERVAL 1 DAY), Jour)

Pourquoi c'était lent sur 1 000 000 de lignes ? Quand on applique une fonction sur une colonne dans un WHERE ou un GROUP BY, MySQL ne peut plus utiliser les index. Il est forcé de lire l'intégralité du million de lignes et de calculer ce IF pour chaque ligne avant de pouvoir filtrer. C'est ce qu'on appelle une requête non-SARGable (Search Argument Able).

2. L'Optimisation Base de Données : Colonne Générée et Index Couvrant
Pour soulager MySQL, nous avons déporté ce calcul lourd au moment de l'insertion plutôt qu'au moment de la lecture.

La Colonne Générée (prod_day) : Nous avons ajouté une colonne virtuelle stockée qui calcule ce décalage de 06h00 automatiquement quand une ligne est insérée.
L'Index Couvrant (Covering Index) : C'est la vraie "magie". Nous n'avons pas juste indexé la date. Nous avons créé l'index idx_summary_covering (prod_day, equipe, cause_id, Duree).
L'astuce technique : Comme cet index contient toutes les données nécessaires pour calculer le résumé quotidien (la date, la durée, et la cause), MySQL n'a plus du tout besoin d'aller lire la table physique sur le disque. Il fait toute l'opération directement en lisant l'index dans la mémoire vive (RAM), ce qui est des dizaines de fois plus rapide.
3. L'Optimisation Code Backend : L'Agrégation en Deux Étapes
Même avec l'index, la requête mettait encore quelques secondes. Le coupable était le INNER JOIN causes.

Le piège de la jointure : Pour calculer l'impact TRS, MySQL joignait la table causes pour chaque arrêt. Sur 30 jours, cela représente environ 165 000 arrêts. Faire 165 000 jointures est lourd.

La solution (Sous-requête) : J'ai réécrit la requête SQL pour inverser l'ordre des opérations :

Pré-agrégation : On groupe d'abord les arrêts par prod_day et cause_id en sommant les durées. Cela réduit nos 165 000 lignes de départ en un tout petit tableau d'environ 600 lignes (30 jours × 20 causes).
La jointure finale : On joint la table causes uniquement sur ces 600 lignes pour récupérer le drapeau affect_trs. On est passé d'une complexité $O(N)$ (où N est le nombre total d'arrêts) à une complexité $O(Jours \times Causes)$.
4. L'Optimisation Frontend : La Fenêtre Coulissante
Dans React (StopsClient.tsx), au chargement initial, les dates fromDate et toDate étaient vides. Cela envoyait une requête au backend lui demandant de calculer le résumé depuis la création de l'usine (soit 1 million de lignes d'un coup !).

La solution : J'ai initialisé les états React avec des dates par défaut (J-30 à Aujourd'hui). Ainsi, dès le premier chargement, le backend ne fouille que dans une "fenêtre" de 30 jours, rendant le tout instantané.
