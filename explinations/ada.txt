Your Query C++ takes 17s at 1M rows because of one remaining bottleneck — the window function forces MySQL to sort all 1M rows before it can compute SUM() OVER (PARTITION BY prod_day, equipe). That sort alone costs ~14 seconds.
The fix your supervisor is hinting at: change the primary key to (prod_day, equipe, id).
InnoDB physically stores rows on disk in primary key order. If data is already sorted by prod_day, equipe on disk, the window function finds the data pre-sorted and skips the sort entirely. That's what makes it behave like C Ultra.

What Indexes Actually Are
Think of a MySQL table like a thick book with 1,000,000 pages (rows), completely unordered.
Without an index: to find all stops from June 2024, MySQL reads every single page — all 1M — checking each one. This is a full table scan.
With an index: MySQL builds a separate, slim, alphabetically-sorted "back-of-book index" that says:
2024-06-01 → pages 3, 47, 891, 1203...
2024-06-02 → pages 12, 88, 902...
It jumps directly to the right pages. 1M rows → maybe 36,000 reads instead.
Types of indexes:
Simple index — on one column:
sqlADD INDEX idx_prod_day (prod_day);
Speeds up WHERE prod_day = '2024-06-01' but MySQL still has to fetch the full row to get Duree, equipe, etc.
Composite index — on multiple columns:
sqlADD INDEX idx_covering (prod_day, equipe, cause_id, Duree);
Works like a phone book sorted by last name, then first name. MySQL can filter by prod_day AND equipe together, much more precise.
Covering index — a composite index that contains every column the query needs:
sql-- Query needs: prod_day, equipe, cause_id, Duree
ADD INDEX idx_covering (prod_day, equipe, cause_id, Duree);
MySQL never touches the main table at all — it answers the entire query from the slim index alone. Like finding your answer in the book's index without ever flipping to the actual pages.
Clustered index (Primary Key) — this is special. InnoDB physically reorders the rows on disk to match the primary key order. There's only one per table. Choosing (prod_day, equipe, id) as your PK means all June 2024 Team 1 stops are literally stored next to each other on disk.
