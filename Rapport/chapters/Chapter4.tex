\chapter{SQL Optimisation}

\section*{Introduction}

\hspace*{\parindent} This chapter documents the complete optimization journey of our MySQL database that collapsed under its own computational weight from the first symptoms of degradation, through systematic diagnosis, to a confirmed final architecture that achieves sub-second response times at full production scale.

\section{\fontsize{15}{18}\selectfont Context and System Overview}

\subsection{\fontsize{14}{17}\selectfont Context}

\hspace*{\parindent} At the start of this project, the database contained a working implementation. The queries returned correct results. The system appeared functional. However, as the dataset grew during testing toward realistic production volumes, a fundamental problem emerged: what worked at a few thousand rows began to show alarming degradation at tens of thousands, and became completely unusable when approaching the million-row scale that real multi-year industrial deployments would inevitably reach.

\subsection{\fontsize{14}{17}\selectfont System Overview}

\subsubsection{\fontsize{13}{16}\selectfont Production Context}

\hspace*{\parindent} The industrial context imposes specific constraints that directly shape every optimization decision:

\begin{itemize}

\item \textbf{Three production teams (\textit{équipes}):} Team 1 works 06:00--14:00, Team 2 works 14:00--22:00, Team 3 works 22:00--06:00.

\item \textbf{Shifted production day:} Stops occurring before 06:00 belong to the \textit{previous} calendar day's Team 3 shift. This introduces a derived \textit{production day} concept that differs from the calendar date.

\item \textbf{Insert-heavy workload:} 2,000--7,000 stop events per day, inserted automatically via machine controllers. Stops are never deleted.

\item \textbf{Dashboard usage:} Up to three supervisors query date-range filtered views throughout each shift. Sub-second response is the target.

\end{itemize}

\subsubsection{\fontsize{13}{16}\selectfont The Key Metric: Percentage of Daily Downtime (PCT)}

\hspace*{\parindent} The primary computed field in every query is the percentage of total downtime that each stop represents within its production day and team:

\begin{equation}
\text{PCT} = \frac{\text{stop duration (seconds)}}{\text{total team downtime for that production day}} \times 100
\end{equation}

This metric is deceptively simple to state but computationally expensive at scale. The denominator requires aggregating all stops for the \textit{same team on the same production day} for every single row in the result. How that aggregation is implemented is the central performance challenge of this entire part.

\section{\fontsize{15}{18}\selectfont Query A: The Original Implementation}

\subsection{\fontsize{14}{17}\selectfont Implementation}

\hspace*{\parindent} The original query was written to correctly compute all required fields for the dashboard: stop times, duration, team assignment, cause information, and the PCT metric. The implementation is shown in Listing 4.1.

\begin{minted}[linenos,bgcolor=codebg,fontsize=\small,frame=lines,framesep=8pt,rulecolor=codeframe,framerule=1.5pt]{sql}
SELECT
    s.Debut AS startTime,
    s.Fin AS stopTime,
    CASE
        WHEN s.Fin IS NULL THEN NULL
        WHEN s.Fin >= s.Debut
            THEN TIME_TO_SEC(s.Fin) - TIME_TO_SEC(s.Debut)
        ELSE (TIME_TO_SEC(s.Fin) + 86400) -
            TIME_TO_SEC(s.Debut)
    END AS duree_secondes,
    (SELECT c.name FROM causes c
        WHERE c.id = s.cause_id LIMIT 1) AS cause,
    (SELECT c.affect_trs FROM causes c
        WHERE c.id = s.cause_id LIMIT 1) AS affect_trs,
    ROUND(
        CASE
            WHEN s.Fin IS NULL THEN NULL
            WHEN s.Fin >= s.Debut
                THEN TIME_TO_SEC(s.Fin) - TIME_TO_SEC(s.Debut)
            ELSE (TIME_TO_SEC(s.Fin)+86400)-TIME_TO_SEC(s.Debut)
        END
    ) * 100.0
    / NULLIF((
        SELECT SUM(
            CASE
                WHEN sx.Fin IS NULL THEN 0
                WHEN sx.Fin >= sx.Debut
                    THEN TIME_TO_SEC(sx.Fin) -
                        TIME_TO_SEC(sx.Debut)
                ELSE (TIME_TO_SEC(sx.Fin)+86400)-
                    TIME_TO_SEC(sx.Debut)
            END
        )
        FROM stops sx
        WHERE DATE_FORMAT(
            IF(sx.Debut < '06:00:00',
                DATE_SUB(sx.Jour, INTERVAL 1 DAY), sx.Jour),
            '%Y-%m-%d'
        ) = DATE_FORMAT(
            IF(s.Debut < '06:00:00',
                DATE_SUB(s.Jour, INTERVAL 1 DAY), s.Jour),
            '%Y-%m-%d'
        ), 0), 2
    AS pct
FROM stops s
WHERE DATE_FORMAT(
    IF(s.Debut < '06:00:00',
        DATE_SUB(s.Jour, INTERVAL 1 DAY), s.Jour),
    '%Y-%m-%d'
) BETWEEN @from AND @to;
\end{minted}

\subsection{\fontsize{14}{17}\selectfont The Root Cause: A Fully Correlated PCT Sub-query}

\hspace*{\parindent} The measured growth follows a quadratic pattern:

\begin{equation}
T_{\text{Query B}}(n) \approx k \cdot n^2
\end{equation}

\hspace*{\parindent} where $n$ is the number of rows and $k$ is a constant representing the per-comparison cost. Compounding this, the correlated subquery uses a non-sargable predicate — \texttt{DATE\_FORMAT(IF(...))} wraps the column in a function call, making it impossible for MySQL to use any index even if one existed on \texttt{Debut} or \texttt{Jour}.

\hspace*{\parindent} The fundamental problem with Query B is the PCT denominator computation. For every single row $s$ in the outer query, MySQL fires a full scan of the entire \texttt{stops} table to compute the daily total.

\section{\fontsize{15}{18}\selectfont Query B: Optimized Implementation}

\subsection{\fontsize{14}{17}\selectfont Motivation}

\hspace*{\parindent} Before restructuring the query, a natural question arises: is it possible to achieve acceptable performance on Query B through index engineering alone, without touching the query itself? This question is not merely academic --- it represents the first instinct of any DBA confronted with a slow query: \textit{add an index}. This chapter documents three systematic experiments that answer this question definitively.

\hspace*{\parindent} Three index strategies are evaluated on identical copies of the \texttt{stops} table (\texttt{stopsB1}, \texttt{stopsB2}, \texttt{stopsB3}), each running the same unmodified Query B against a different index configuration. The results draw a clear line between what indexing can and cannot accomplish.

\subsection{\fontsize{14}{17}\selectfont Experimental Setup}

\hspace*{\parindent} Three copies of the \texttt{stops} table were created with identical data but different index configurations. Each benchmark table contains approximately 10,000 rows, representative of roughly one week of real industrial data at 1,200 stops per day.

\subsection{\fontsize{14}{17}\selectfont Experiment B2: Functional Index}

\subsubsection{\fontsize{13}{16}\selectfont Hypothesis}

\hspace*{\parindent} MySQL 8.0 supports \textit{functional indexes} --- indexes on expressions rather than raw columns. If the index stores the exact value of \texttt{DATE\_FORMAT(IF(Debut < '06:00:00', DATE\_SUB(Jour, INTERVAL 1 DAY), Jour), '\%Y-\%m-\%d')} for every row, then the correlated subquery's \texttt{WHERE} clause, which tests exactly that expression, should be able to use the index and avoid the full table scan.

Functional indexes, while theoretically attractive, provide no measurable improvement for this particular query structure.

\subsection{\fontsize{14}{17}\selectfont Experiment B3: Covering Index}

\subsubsection{\fontsize{13}{16}\selectfont Hypothesis}

\hspace*{\parindent} A \textit{covering index} contains every column that a query touches, allowing MySQL to read from the index structure instead of the main table rows. Even when the predicate is non-sargable (so the index cannot \textit{filter} rows), a covering index can still be used as the \textit{scan source} --- replacing expensive main-table page reads with cheaper, denser index reads.

\hspace*{\parindent} The covering index for Query B must include every column referenced in the \texttt{SELECT} list, the \texttt{WHERE} clause, and the correlated subquery:

\begin{minted}[linenos,bgcolor=codebg,fontsize=\small,frame=lines,framesep=8pt,rulecolor=codeframe,framerule=1.5pt]{sql}
ALTER TABLE stopsB3
  ADD INDEX idx_covering_queryb (Jour, Debut, Fin, cause_id);
\end{minted}

\textit{Listing 4.4: Covering index definition for stopsB3}

\subsubsection{\fontsize{13}{16}\selectfont Results}

\hspace*{\parindent} The covering index provides modest improvement by reducing the I/O cost of table scans, but the fundamental O(n$^2$) complexity remains unchanged. In big data systems, the equivalent lesson is equally fundamental: columnar storage, predicate pushdown, and partition pruning all reduce the \textit{constant factor} in a computation --- they do not change the algorithmic complexity class. A full O(n$^2$) Cartesian join remains O(n$^2$) even on Apache Spark, no matter how the data is partitioned. Only query restructuring --- moving from a nested scan to a pre-aggregated hash join --- changes the exponent. Indexes are a multiplier on good architecture, not a replacement for it.

\end{tcolorbox}

\section{\fontsize{15}{18}\selectfont Query C: Breaking the Quadratic Loop}

\subsection{\fontsize{14}{17}\selectfont The Targeted Fix}

\hspace*{\parindent} Having identified the correlated PCT subquery as the sole cause of Query B's collapse, the first intervention was surgical: replace the per-row full scan with a single pre-aggregated \texttt{JOIN}. The daily totals are computed once in a derived table and joined against the main query. All other problems are intentionally left untouched to allow the impact of this single change to be measured cleanly.

\begin{minted}[linenos,bgcolor=codebg,fontsize=\small,frame=lines,framesep=8pt,rulecolor=codeframe,framerule=1.5pt]{sql}
SELECT
    s.Debut AS startTime,
    s.Fin AS stopTime,
    CASE
        WHEN s.Fin IS NULL THEN NULL
        WHEN s.Fin >= s.Debut
            THEN TIME_TO_SEC(s.Fin) - TIME_TO_SEC(s.Debut)
        ELSE (TIME_TO_SEC(s.Fin) + 86400) -
            TIME_TO_SEC(s.Debut)
    END AS duree_secondes,
    (SELECT c.name FROM causes c
        WHERE c.id = s.cause_id LIMIT 1) AS cause,
    (SELECT c.affect_trs FROM causes c
        WHERE c.id = s.cause_id LIMIT 1) AS affect_trs,
    ROUND(
        CASE
            WHEN s.Fin IS NULL THEN NULL
            WHEN s.Fin >= s.Debut
                THEN TIME_TO_SEC(s.Fin) - TIME_TO_SEC(s.Debut)
            ELSE (TIME_TO_SEC(s.Fin)+86400)-TIME_TO_SEC(s.Debut)
        END
    ) * 100.0 / NULLIF(dt.day_total, 0),
    2
    ) AS pct
FROM stops s
JOIN (
    SELECT
        DATE_FORMAT(IF(sx.Debut < '06:00:00',
            DATE_SUB(sx.Jour, INTERVAL 1 DAY),
            sx.Jour), '%Y-%m-%d') AS prod_day,
        SUM(CASE
            WHEN sx.Fin IS NULL THEN 0
            WHEN sx.Fin >= sx.Debut
                THEN TIME_TO_SEC(sx.Fin) -
                    TIME_TO_SEC(sx.Debut)
            ELSE
                (TIME_TO_SEC(sx.Fin)+86400)-
                TIME_TO_SEC(sx.Debut)
        END) AS day_total
    FROM stops sx
    GROUP BY prod_day
) AS dt ON DATE_FORMAT(
    IF(s.Debut < '06:00:00',
        DATE_SUB(s.Jour, INTERVAL 1 DAY), s.Jour),
    '%Y-%m-%d'
) = dt.prod_day;
\end{minted}

\section{\fontsize{15}{18}\selectfont Query D: The Window Function Hypothesis}

\subsection{\fontsize{14}{17}\selectfont The Reasoning Behind the Attempt}

\hspace*{\parindent} After Query C reduced execution from an estimated 73 days to 46.642 ms at one million rows, the next question was: can we improve further without a full schema redesign? The \texttt{EXPLAIN ANALYZE} profile of Query C reveals two distinct table scans --- one for the main \texttt{SELECT} and one inside the pre-aggregated derived table. A natural hypothesis emerged: SQL window functions could collapse these into a single pass.

\hspace*{\parindent} The function \texttt{SUM(Duree) OVER(PARTITION BY prod\_day, equipe)} computes each row's group total inline, during the same pass that reads the row --- theoretically eliminating the separate pre-aggregation scan and the subsequent \texttt{JOIN}. In theory, this means:

\begin{itemize}

\item One scan instead of two

\item No CTE or derived table materialization

\item No hash join probe loop

\end{itemize}

\hspace*{\parindent} The hypothesis was compelling enough to test rigorously before committing to a full schema redesign.

\subsection{\fontsize{14}{17}\selectfont Implementation}

\begin{minted}[linenos,bgcolor=codebg,fontsize=\small,frame=lines,framesep=8pt,rulecolor=codeframe,framerule=1.5pt]{sql}

FROM (

        s.Debut, s.Fin, s.Duree, s.prod_day, s.equipe,
        c.name, c.affect_trs,
        ROUND(
            s.Duree * 100.0 / NULLIF(
                SUM(s.Duree) OVER (PARTITION BY s.prod_day, s.equipe),
            0), 2

    JOIN causes c ON c.id = s.cause_id

\subsection{\fontsize{14}{17}\selectfont Root Cause: Sort Buffer Spill to Disk}

\hspace*{\parindent} The limited improvement --- and the failure to surpass Query C's eventual 2,200 ms --- is caused by how MySQL 8.0 implements window function evaluation internally.

\subsubsection{\fontsize{13}{16}\selectfont How MySQL Executes Window Functions}

\hspace*{\parindent} Unlike a pre-aggregation approach --- which produces a compact intermediate result --- a window function must hold all rows belonging to a partition in memory simultaneously before it can emit any output row. The execution sequence is:

\begin{itemize}

\item Read all 1M rows from the covering index scan.

\item Sort all 1M rows by (prod\_day, equipe) to group partitions.

\item For each partition, accumulate rows in a sort buffer.

\item Compute SUM(Duree) over the buffered partition.

\item Emit rows for that partition with the computed total.

\end{itemize}

\section{\fontsize{15}{18}\selectfont Query E: Big Data Principles Applied to MySQL}

\hspace*{\parindent} The window function hypothesis tested in Chapter 5 demonstrated that standard MySQL session-level constraints prevent a single-pass approach from outperforming a two-pass pre-aggregation strategy at production scale. Improving on Query D's 25,955 ms result required addressing the root problem differently: not eliminating a scan, but making every scan as efficient as physically possible through comprehensive schema-level redesign.

\hspace*{\parindent} This chapter presents the final, fully optimized architecture. The solution requires no auxiliary tables, no triggers, and no scheduled events --- only a redesigned table schema with stored generated columns, a carefully chosen set of indexes, and a single optimized SQL query.

\subsection{\fontsize{14}{17}\selectfont Schema Redesign}

\subsubsection{\fontsize{13}{16}\selectfont Stored Generated Columns}

\hspace*{\parindent} \textbf{Problem solved:} Non-sargable \texttt{DATE\_FORMAT(IF(...))} and inline \texttt{CASE TIME\_TO\_SEC(...)} recomputed on every row in every query version to date.

\hspace*{\parindent} \textbf{Solution:} MySQL's \texttt{GENERATED ALWAYS AS ... STORED} creates columns whose values are computed automatically at insert time and stored physically on disk. The expression runs once per row at write time instead of millions of times per query. The complete schema definition is shown in Appendix~\ref{app:optimized_schema_b}.

Stored generated columns prod\_day, equipe, and Duree are computed once at insert time. All subsequent reads find pre-computed values. This is the feature store pattern used in Databricks, MLflow, and all major data warehouse platforms --- shift expensive computation from read time to write time.

\end{tcolorbox}

\subsection{\fontsize{14}{17}\selectfont The Optimized Query}

\hspace*{\parindent} The final optimized query combines the pre-aggregation approach with the redesigned schema's stored generated columns and covering indexes. The query uses a Common Table Expression (CTE) to compute daily team totals efficiently, then joins the results with a covering index scan to minimize I/O.

\begin{minted}[linenos,bgcolor=codebg,fontsize=\small,frame=lines,framesep=8pt,rulecolor=codeframe,framerule=1.5pt]{sql}
-- Benchmark harness
SET @total_rows = (SELECT COUNT(*) FROM stops);
SET @t        = NOW(6);

SELECT COUNT(*) INTO @row_count
FROM (
    WITH day_team_totals AS (
        SELECT
            prod_day,
            equipe,
            SUM(Duree) AS day_total
        FROM stops
        FORCE INDEX (idx_covering)
        GROUP BY prod_day, equipe
    )
    SELECT
        s.Debut,
        s.Fin,
        s.Duree,
        s.prod_day,
        s.equipe,
        c.name,
        c.affect_trs,
        ROUND(
            s.Duree * 100.0 / NULLIF(dt.day_total, 0),
            2
        ) AS pct
    FROM stops                s FORCE INDEX (idx_covering)
    JOIN causes               c ON c.id = s.cause_id
    JOIN day_team_totals     dt ON dt.prod_day = s.prod_day
                                AND dt.equipe   = s.equipe
) AS q;

SET @elapsed = TIMESTAMPDIFF(MICROSECOND, @t, NOW(6)) / 1000.0;
INSERT INTO perf_results (version, total_rows, elapsed_ms, row_count)
VALUES ('C_CTE_final', @total_rows, @elapsed, @row_count);

SELECT 'C_CTE_final' AS query, @total_rows AS total_rows,
       @row_count AS row_count, CONCAT(@elapsed, ' ms') AS elapsed;
